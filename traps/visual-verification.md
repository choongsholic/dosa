# 시각 검수 함정 — 도사 자체 렌더·자체 판독 게이트

## 핵심 원칙

도사가 **직접 슬라이드를 PNG로 렌더하고 그 이미지를 Read 툴로 보면서 시각 검수**한다. 사용자에게 스크린샷 떠 달라고 하지 않는다 — 도사 워크플로의 일부로 자동 수행.

> *왜 마크업만으론 안 되는가*: HTML/CSS 룰이 맞아도 카드 안 텍스트 양 차이로 카드 높이가 어긋나거나, 셀 텍스트 길어 행 높이가 들쑥날쑥, `--accent` 분포가 시선을 흩뜨리는 등 *렌더된 결과* 에서만 드러나는 함정이 다수. 코드 검증으론 못 잡는다.

## 렌더 도구

`~/.claude/skills/dosa/_render/render.js` 사용.

```bash
node ~/.claude/skills/dosa/_render/render.js <work-html-path>
# → <work-dir>/_renders/slide-01.png ~ slide-NN.png 생성
```

다크/라이트 양쪽 검수 필요시:
```bash
DOSA_THEME=both node ~/.claude/skills/dosa/_render/render.js <work-html-path>
```

처음 셋업 (다른 컴퓨터에서 `도사 풀` 후 1회):
```bash
cd ~/.claude/skills/dosa/_render && npm install
```

## 참조 디자인 처리 (필수 — 자동 비교)

**도사 작업물은 반드시 참조 디자인이 존재한다.** 이걸 *옵션*으로 두면 빠뜨리게 됨 (실제 발생 사례: 2026-05-09 condolence 작업에서 cover-label/author/date 톤이 베이스와 어긋났는데 도사가 비교 안 함 → 사용자 지적).

### 참조 우선순위 (있는 것부터 사용)

1. **사용자 지정 참조** — *"이 톤으로 따라가줘"* 식으로 명시한 다른 HTML/이미지. 변환 시작 시 사용자가 알려줌
2. **베이스 dashboard.html** (`~/.claude/skills/dosa/aqua-dashboard/dashboard.html`) — 항상 존재. 기본 비교 대상
3. **작업물 폴더의 `참고/` 자료** — 콘텐츠 검증용 PNG/PDF가 있다면 *콘텐츠 정확성* 도 함께 검수

### 비교 절차

도사가 시각 검수 단계에서 자동으로:

```bash
# 작업물 렌더
node ~/.claude/skills/dosa/_render/render.js <work-html-path>

# 베이스/참조 렌더 (한 번만)
node ~/.claude/skills/dosa/_render/render.js <reference-html-path> /tmp/ref-renders
```

작업물 슬라이드별로 *같은 컴포넌트를 쓰는 베이스 슬라이드*를 짝지어 Read 툴로 나란히 비교:
- **커버**: 작업물 p1 ↔ 베이스 p1 (`slide-cover` 패턴 — 단, `design.md` 3.1절 보고형/매뉴얼형 구분 적용)
- **인트로**: 작업물의 `slide-intro` ↔ 베이스의 `slide-intro` (intro-cards 톤)
- **표**: 작업물의 `xt-block` ↔ 베이스 동일 컴포넌트 (위계·강조·라벨)
- **카드 그리드**: `lc-cards` / `bh2` / `pat4` 등 같은 컴포넌트끼리

### 비교에서 잡아야 할 것

- 베이스에 있는 요소가 작업물에 *빠진* 경우 (또는 그 반대)
- 같은 컴포넌트인데 폰트 크기·여백·정렬이 *어긋난* 경우
- 베이스의 시각 톤(예: cover-author weight 700)과 작업물의 톤(예: weight 600) 차이

### 콘텐츠 참고 자료 활용

작업물 폴더에 `참고/` 또는 `references/` 가 있으면:
- 자료(PDF, PNG, 노션 캡처 등)를 Read 툴로 읽고 작업물 텍스트와 대조
- *지방 배송 시 1단 30 · 2단 …* 처럼 끊긴 텍스트의 정답을 찾을 수 있음
- *유물 시간 → 발인 시간* 처럼 오타 정답을 확정 가능
- **변환 단계에서 OCR·압축으로 잘린 텍스트는 거의 항상 참고 자료에 정답이 있음**. 검수에서 참고 자료를 안 보면 추측만 가능

이 단계는 *텍스트 검수* 와 겹치지만 — 시각 검수 시 참고 자료를 함께 펼쳐 보면 양쪽 검수가 합쳐져 효율적.

## 시각 검수 8종 게이트

PNG 슬라이드 한 장씩 Read 툴로 보면서 다음 8가지를 점검. 한 슬라이드에서 의심 발견 시 메모 → 마지막에 종합 보고.

### 1. 카드 높이 정합 + 슬라이드 밀도

가로 그리드 카드(`lc-cards`, `bh2`, `intro-cards`, `pat4`, `ba-cards`)에서 *두 가지를 같이* 본다 — 끝선만 보면 함정.

**1-a. 끝선 정합**
- 카드 위·아래 끝선이 맞는가
- 안 텍스트 양이 달라 한 카드만 길어진 경우 — `align-items: stretch` 미작동 또는 `min-height` 필요

**1-b. 슬라이드 하단 여백 / 콘텐츠 밀도**
- 끝선이 정합돼도 *슬라이드 하단이 텅 비지 않고 카드가 1/3 이상 비우지 않게 빡빡하게 차있는지* 따로 봐야 함
- 베이스 `bhx-card` 패턴은 `body { flex: 1 }` 라서 카드가 *세로로 늘어나 슬라이드를 채워버림*. 콘텐츠 적은데 카드만 늘어 있으면 시선 안정감 깨짐 — *밀도가 가짜로 올라간 상태*.
- 매뉴얼/안내 같은 정보 밀도 낮은 슬라이드, 또는 좌우 카드 정보량 격차 큰 슬라이드에서 자주 발생 (실제 사례: 2026-05-09 condolence p10 contact info — 좌 4블록·우 3블록, 둘 다 stretch로 슬라이드 가득 채워서 무거워 보임)

**카드 stretch 끄는 조건**
- 슬라이드 콘텐츠 양이 적음 (정보 밀도가 낮은 슬라이드)
- 좌우 카드 정보량 격차가 크게 차이남 (한쪽이 한쪽보다 *눈에 띄게* 짧음)

이 경우 자연 높이 — `align-items: start` + 카드 자체 `min-height` 제거 → 카드 높이는 콘텐츠가 결정, 슬라이드 하단 여백 확보. 끝선 어긋나도 *그게 콘텐츠를 정직하게 반영*하는 결과라 OK.

> *주의*: "카드 높이 같음" 룰은 *항상 옳은 것이 아님*. 슬라이드 단위로 판단 — 문서 유형(매뉴얼/보고) 분기가 아님.

### 2. 텍스트 오버플로·강제 줄바꿈
- 셀/카드 본문이 한 단어 넘침, 두 줄로 깨짐, ellipsis로 잘림
- 한국어+긴 영문 혼합 케이스(직책+한글 이름 등) 특히 주의
- 같은 컬럼 셀들의 *행 높이 일관성* 도 함께 봄

### 3. 여백·중심 균형
- `attn-center` 본문이 슬라이드 *수직 중앙* 에 자연스럽게 떠 있는지
- 좌우 여백이 한쪽만 비거나 꽉 찬 곳 없는지
- `slide-intro`의 상/중/하 3구역(design.md 11절) 분배 의도대로인지

### 4. 강조 절제
- `--accent`·`row-hl`·`<li class="hl">`·`badge-discuss` 사용 빈도
- **슬라이드당 강조 1~2곳** 권장. 매트릭스 표는 `row-hl` 1행, 본문 `hl` bullet 1개 정도
- "이 슬라이드 시선이 어디 가야 하나?" 한 군데로 답이 나와야 통과

### 5. xt-block 위계 (본문 prominent / 헤더 차분)
- 헤더 셀이 본문 셀보다 **작고 차분** 한지 (design.md 13.7절)
- `--xt-headline-fs(16px) < --xt-cell-fs(26px)` 룰. 사진상 헤더가 더 굵거나 크면 위계 역전 — 즉시 수정
- 동어 반복 컬럼은 `formula-notes` 로 빼기

### 6. 빈약한 페이지 / 과밀 페이지
- *빈약*: 타이틀+짧은 bullets 만, 본문 영역 1/3이 텅 빔
- *과밀*: 카드 4개+긴 본문+표 한 장에 몰림
- 슬라이드 N장 전체의 *시각적 밀도가 균일* 한지

### 7. 다크/라이트 모드 양쪽 가독성
- 텍스트가 배경에 묻히는 곳 (특히 `--text-secondary` 옅음)
- 카드 헤더 검정 박스가 다크 모드에서 *배경에 묻혀* 카드 경계 사라지는 케이스
- 이미지(`dash-wrap`)가 모드 전환 시 떠 보이는 곳

### 8. 시선 흐름
- 첫 시선: `doc-title`(좌상단) → `doc-bullets` → 본문(중앙) → 강조 → 하단 노트
- 자연스럽게 위→아래·좌→우로 흐르는지
- 강조가 시선을 *역행* 시키는 위치에 있으면 사용자가 두 번 읽어야 함

## 검수 보고 형식

PNG 다 본 뒤 슬라이드별 발견을 표로 정리:

```
시각 검수에서 잡힌 N건:
- p3 표: 헤더 폰트가 본문보다 굵음 — 위계 역전
- p4 lc-cards: 가운데 카드만 본문 4줄 → 카드 높이 어긋남
- p6 매트릭스: 강조 행이 3행 → 강조 의미 약화. 1행만 row-hl 권장
- p9 (다크): 검정 헤더가 배경과 거의 같은 톤이라 카드 경계 사라짐
- 전체: --accent 색상이 6장에 등장 → 사용처 정리 필요
```

지적 영역에 따라:
- **CSS 토큰/스타일 조정** (예: `--xt-headline-fs` 12px) → 도사 자동 반영 OK, 사용자에게 보고
- **레이아웃 변경** (카드 분할/병합) → 사용자 확인 후 반영
- **콘텐츠 분량 조정** → 사용자에게 의견 요청

## 효율 팁

- N장 전부 보지 말고 **표/매트릭스 슬라이드 → 카드 그리드 슬라이드 → 첫 장·마지막 장** 순으로 우선
- 의심 안 가는 텍스트-only 슬라이드는 빠르게 패스
- 다크 모드 검수는 *전부 다 다시 보지 말고* 카드 헤더·강조 색이 들어간 슬라이드만 표본 추출
- 렌더 결과(`_renders/`)는 검수 후 폐기 대상 — `.gitignore` 됨, 작업물 폴더에 남아도 OK
